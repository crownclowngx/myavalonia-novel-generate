## 2. 实施原则与工程落点

### 2.1 必须贯穿各阶段的产品约束

1. 一本书一个独立项目和工作区；两个共享 Tool 分别管理模板和模型连接。
2. 正文、设定、规则和修订以本书数据为准。采用模板保存本书快照，模板升级不自动覆盖作品。
3. API Key 与模板、项目和导出分离；连接绑定明确，运行参数冻结，不使用可变的全局“当前书/当前模型”。
4. 自动生成是主流程：范围、费用预算、修正次数和停止条件明确后连续推进，通过章不逐章等待接受。
5. 编辑保存、工作稿提交、人工定稿是三种操作。工作稿记忆与正式故事状态隔离，正文和对应记忆必须一致提交。
6. 规则必须保存、逐请求装配、检查、有限修正并留下记录；检查失败与未检查不能当作通过。
7. 模型只返回文本或结构化候选，不直接执行脚本、数据库写入、任意文件操作或开放式工具调用。
8. 网络取消不取消必要的本地恢复保存。失败、退出和重新打开都保留清晰的恢复入口。
9. 主流程无需 Workflow Studio、外部数据库服务、容器、本地模型运行时或向量服务。
10. 用真实文本、实际文件和故障注入验证风险；类型存在、编译通过、模型自评分和 HTML 示意均不能代替产品验收。

以下是在现有生产项目中逐步建立的目录，不要求在 G0001 一次生成所有空壳。

测试先放在现有 `tests/NovelGeneratePlugin.Tests` 中，按 `Domain`、`Persistence`、`Generation`、`Lifecycle`、`Presentation` 等主题组织。确需 Avalonia Headless 或跨 ALC 测试时再增加测试依赖或独立测试项目，不能把测试和 Fake 带进生产包。

### 3.3 推荐推进方式

主线先顺序完成 G0001–G0016。G0007 是“无网络也可安全使用”的阶段出口，G0011 是内部单章切片，G0016 才是首个可用自动创作版本。

不按未经验证的速度填写工期或发布日期。每阶段结束先核对证据和剩余工作，再推进依赖它的阶段。技术验证失败时按该阶段的收缩方案处理；不能绕过数据、凭据、检查与预算要求继续假装具备自动创作能力。

## 10. 验证、风险与阶段出口

### 10.1 分层验证

| 层次 | 主要证据 | 不能替代 |
| --- | --- | --- |
| 领域与应用测试 | 状态转换、规则、版本、预算、依赖和确定性故障夹具 | 真实文件、真实 UI 或文学质量 |
| 实际文件与协议测试 | SQLite 事务/备份/迁移、HTTP/SSE、截断和取消 | 真实服务商可用性或真实 Host |
| UI/Standalone/Headless | 绑定、视图状态、主题尺寸、交互与资源释放 | 原生文件选择器、Dock、真实 ALC/宿主生命周期 |
| 真实 Host | 贡献、加载、私有资产、双书/Tool、关闭重启、原生交互 | 作者接受率和服务商计费结果 |
| 受预算真实样稿 | 实际文本、用量、未知费用、作者修改成本和长期表现 | 规则与事务故障的穷尽验证 |
| 交付验收 | 配对正式包、安装、升级、恢复和摘要 | 功能已实现或已实际发布 |

本地命令模板、秘密处理、结果格式和证据要求见[质量基线](refactoring/quality-baseline.md)。每阶段只运行适用检查；纯文档变更检查路径与状态，不重复运行小说业务测试。

### 10.2 重点不确定项与处理归属

| 不确定项 | 首次验证 | 验证失败时处理 |
| --- | --- | --- |
| 私有 SQLite/中文检索资产能否在实际 Host 使用 | G0002、G0007、G0009 | 修复包声明；检索可收缩为有界实体/文本查询，不牺牲来源和状态过滤 |
| 模型流/结构化响应与能力参数是否符合预期 | G0008 | 更新适配和能力矩阵；不支持项明确禁用，不伪造成功 |
| 上下文预算是否足以装入必需规则 | G0009 | 发请求前报告冲突并调整任务/规范，不能隐式删规则 |
| 单章质量返工是否过多 | G0011、G0016 | 保留有限次数和暂停，按真实样稿调整默认策略 |
| 材料方法和文风规范是否实际改善作品 | G0013、G0018、G0020 | 保存对照样稿与差例，撤销无效规范，不用总结长度证明有效 |
| 30–50 章性能与记忆稳定性 | G0017、G0019、G0020 | 优先修来源/状态/检索和 UI 瓶颈，不默认引入外部服务 |
| 非纯文本材料质量与发行成本 | G0024 | 保留文字输入路径，未验证格式继续不开放 |
| 语义检索是否具有净收益 | G0026 | 不开放或默认关闭，保留已验证的结构化检索 |
| 完整 Host 或真实模型评测环境暂不可用 | 对应阶段 | 继续完成独立本地工作，将缺失验收明确记录，不将阶段冒充完整通过 |

### 10.3 每阶段结束必须留下的记录

每个 `result.md` 至少写明：日期、真实基线/源码摘要、变更范围、已完成的工作项、实际命令与环境、测试和人工结果、相关 A/FR 编号、失败与偏差、尚未完成的检查以及下一阶段入口。

通过、失败、未执行、环境缺失、不适用分别记录。使用过的测试数量和截图必须属于当前变更版本，不从其他插件或历史阶段复制。发现缺陷先保留回归场景，再修实现，不能以删测试或改完成口径制造通过。
