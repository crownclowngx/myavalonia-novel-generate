# 整本小说分析可行性与实施计划

日期：2026-09-12
版本：v0.1
项目：`myavalonia-novel-generate` / `NovelGeneratePlugin`
实施编号：G0029–G0036
当前状态：G0029–G0032 已验收；累计 4/8 阶段、20/40 工作项；最终产品目标尚未达到。

本文承接用户确认的需求：给出一部 TXT 小说，系统自动分析完整正文，提取背景世界观、人物与关系、角色目标与任务、故事结构、文风和主题，再综合形成有原文依据的结论。最初轮次仅编制计划；用户随后已授权按阶段实施，具体实现与验证以阶段结果为准。

相关入口：[实施总计划](implementation-plan.md) · [阶段索引](refactoring/README.md) · [质量基线](refactoring/quality-baseline.md) · [原 G0021 规划](implementation-plan.md#g0021)。

## 1. 最终目标与范围

### 1.1 用户最终得到什么

用户在插件中选择一本 TXT，核对分章与全文范围，选择已有模型连接并设置预算，点击开始。系统持续完成全文提取、跨章节整合、专题分析和综合报告；正常处理不要求用户逐章确认。遇到预算、连接或无法自动解决的问题时保存进度并给出明确恢复入口。

完成后，用户可以在插件中阅读、保存并导出以下结果：

| 报告部分 | 必须回答的问题 |
| --- | --- |
| 全书概览与综合结论 | 这是什么类型的故事，核心冲突是什么，最鲜明的特色是什么，各要素如何共同形成阅读效果 |
| 背景世界观 | 时代、地理、组织、社会制度、力量或职业体系有哪些规则、代价、限制和例外 |
| 人物与关系 | 主要人物是谁，有什么动机，如何变化，关系如何演进，在故事中起什么作用 |
| 角色目标与任务 | 谁要完成什么，为什么做，遇到哪些阻碍，采取什么行动，得到什么结果 |
| 故事结构 | 主支线、阶段目标、关键事件、冲突升级、转折、伏笔、回收和结局如何组织 |
| 文风 | 视角、句式、用词、对白、描写、节奏、情绪有哪些具体特征，是否随阶段或人物变化 |
| 主题与评价 | 人物选择和结局回应什么价值冲突，有哪些有依据的优点、问题与可借鉴方法 |
| 来源与分析说明 | 实际处理了哪些原文，结论依据在哪里，哪些是推断，哪些仍不确定或存在冲突 |

综合结论必须连接各维度，例如解释“世界规则如何形成角色困境，动机如何驱动主线，叙述方式如何加强悬念，结局如何回应主题”。只拼接几份摘要不算完成综合分析。

### 1.2 首次交付范围

- 单本本地 TXT；支持 UTF-8、带 BOM 的常见 Unicode 文本和 GB18030，编码不确定时提供预览与切换。
- 完整正文处理，可靠分章或按段落划分片段；超长章节继续拆分。可中途查看部分结果，默认任务目标仍为全文。
- 六个专题：世界观、人物关系、目标任务、故事结构、文风、主题；另有全书综合结论。
- 原文依据定位、自动保存、暂停、取消、中断恢复、预算和已知/未知用量展示。
- 原生 Avalonia 界面、离线阅读已保存报告、Markdown 报告导出，导出包含必要引用和覆盖说明。
- 首版候选容量为单书不超过 200 万个 .NET 字符串字符且文件不超过 20 MiB；这是待 G0029 固定并由 G0036 验证的设计目标，当前尚未支持。字符数使用 UTF-16 计数，不能标为精确汉字数或 token 数。

模板采用、多书融合、已有小说续写、自动创作、网站采集、PDF/OCR、向量服务和关系图可视化归属后续扩展。报告本身完整可用，不以生成新书为前提。

### 1.3 最终完成的判断

只有 G0036 的全文实测、质量评阅、恢复和真实 Host 交互验收满足本文标准，才能写“整本小说分析目标已达到”。以下状态分别记录：

| 状态 | 含义 |
| --- | --- |
| 计划已编制 | 目标、方案、工作项和验收口径已经写明 |
| 工程已验证 | 对应实现及适用自动化检查通过 |
| 全文任务已完成 | 本次输入的全部正文单元与报告阶段完成，覆盖数据一致 |
| 产品目标已达到 | 必需工程、真实模型、人工质量及桌面流程均有通过证据 |
| 已发布 | 另有 G0028 正式发行与交付记录 |

全文处理覆盖率不等于语义分析准确率；真实调用成功、模型自评分或测试数量不能替代文学分析质量。

### 2.2 判断与主要工作量

结论：可在现有 Plugin 生产程序集内增量实现。模型连接、请求管理、SQLite、UI 注册与关闭协调均有基础，当前不需要修改公共 SDK 或引入外部数据库服务。

主要新增工作集中在：全文输入和定位、结构化提取、跨章节身份与时序整合、分层汇总、持久化运行调度、报告界面和质量评测。最大的质量风险是人物错误合并、压缩丢失关键事实、将角色说法当客观事实，以及对文风作出缺乏原文支持的泛化判断。

## 4. 处理流程与数据设计

### 4.1 从 TXT 到结论

```text
选择 TXT → 编码/分章预览 → 保存不可变来源快照 → 构建全文分析单元
    → 逐单元多维提取 → 跨章节实体、规则、事件与关系整合
    → 卷/阶段分层汇总 → 六个专题报告 → 交叉核对与全书综合结论
    → 报告阅读、原文定位、保存与 Markdown 导出
```

第一轮每个单元一次提取多个维度，输出有界 JSON，字段包括：内容摘要、世界规则、人物提及、事实和事件、角色目标、关系变化、伏笔线索、文风观察、主题线索、证据与不确定项。密集单元装不下输出时缩小或拆分单元，不能因 JSON 截断就把缺失字段当空结果。

单元大小按模型输入、预留输出、契约和上下文余量共同计算。约 4,000–8,000 字符仅作为中文正文切分的初始调参范围，不是远端 token 上限。首轮可以提供前后少量上下文或相关身份线索，其输入版本必须加入依赖指纹。

### 4.2 原文与覆盖

- 保留来源原始字节或其不可变快照及解码文本、编码、哈希、版本；规范化文本要有定位映射，不能直接拿规范化偏移回跳原文件。
- 每个单元有独立正文区间；补充上下文和重叠区间仅帮助理解，不重复计入全文覆盖。
- 分章清单明确序言、正文、后记和用户排除内容。不会静默删除疑似广告或目录；排除内容在预览中列出。
- 覆盖率以目标正文区间的并集计数。只有通过结构、证据校验并持久化的单元才计入“已完成提取”。
- 多轮结果按来源、分析方案、提示词和模型配置版本区分；部分结果可读，完整报告标志需所有必需阶段完成。

### 4.3 跨章整合与分层汇总

人物先形成带原文定位的提及，再建立候选身份映射。相同名称不直接证明同一身份，别名合并需要证据；歧义保留为待确认，修正身份映射时更新相应依赖结果。人物状态和关系保留变化记录。

事件同时记录文本顺序、故事时间线索、发生状态、叙述来源以及证据。客观叙述、人物发言、传闻、假设、梦境、回忆和分析推断分别标记。无法确定时间或真伪时允许未知。

汇总按实际卷或有界章节组组织，每次仅装入预算允许的输入；上一层仍太大时继续分层。除阶段摘要外，实体、事件、规则、未解决问题及来源索引持续保留。专题分析可按实体、关键词、章节和事件找回原文，避免依赖单一滚动摘要。综合阶段新增的事实必须由可追溯证据支持，不能由汇总过程自行补造。

文风专题直接读取有代表性的原文片段，覆盖前中后期、对白与叙述及主要场景；同时保存选择规则和覆盖范围。确定性句长、标点、对白占比等可作为辅助统计，但须明确算法和适用范围。

### 4.4 新增职责建议

以下名称是建议内部组件，不表示已有文件或公共 API。保持现有 Domain/Application/Infrastructure/Features 分层，不为概念数量额外拆项目。

| 组件 | 主要职责 |
| --- | --- |
| `ReferenceBook`、`SourceSnapshot`、`AnalysisChunk` | 分析书身份、来源版本、章节和区间 |
| `AnalysisEvidence`、`ReferenceEntity`、`ReferenceEvent` | 证据、参考书实体、时序及关系 |
| `AnalysisRun`、`AnalysisNode`、`NovelAnalysisReport` | 运行计划、依赖节点、状态及版本化报告 |
| `NovelImportService` | 解码、分章、切块、来源快照和覆盖清单 |
| `NovelChunkAnalysisService` | 组装第一轮输入并验证多维提取结果 |
| `ReferenceIntegrationService` | 实体归并、事件和规则整合及冲突处理 |
| `ReferenceContextBuilder`、`NovelSynthesisService` | 选择相关证据、分层汇总、专题与综合报告 |
| `NovelAnalysisService` | 编排持久化节点、预算、取消、恢复及版本失效 |
| `ReferenceAnalysisStore` | SQLite 事务、节点检查点、源快照和报告保存 |
| `NovelAnalysisPanel`、报告阅读视图 | 用户操作、进度、证据跳转和报告导出 |

建议新建独立 SQLite 分析库，逻辑上分离书目、来源、章节、分析单元、运行节点、结果、证据、实体事件和报告。大文本按需读取、列表分页，完成一个节点只写相关记录。运行结果与节点完成状态在同一本地事务中提交。

当前请求账本中的 `BookId` 在短材料任务中已用作独立材料所有者。本专项需明确它映射到独立参考书身份，并在运行元数据中保存所有者类型；分析记录不能被当作创作项目正文或已接受故事事实。

### 4.5 长任务、预算和恢复

运行状态建议为：待开始、运行中、暂停、需要处理、已完成、已取消、失败、中断。节点状态区分待执行、在途、已完成、失败和依赖失效。隐藏工具不丢失任务；关闭某个创作项目不取消参考书分析；退出插件时取消网络并完成必要的本地保存。

发出请求前，持久化节点与操作 ID 的关联，再通过现有请求服务预留预算和发送。恢复时先核对账本：已保存的有效完整响应可恢复节点结果；Reserved/Running 等不确定结果保留，不承诺远端恰好执行一次，也不静默重发。

缓存键包含来源哈希、切分规则、任务类型、提示词/输出契约版本、冻结模型配置和依赖结果指纹。源变化使对应提取及下游汇总失效；只改综合提示词可复用合规的提取结果。缓存失效保留历史报告，不覆盖旧版本的来源说明。

预算是整次分析共享的总约束，覆盖提取、整合、分层汇总、专题、综合、补查和重试。开始前预留后续汇总额度，不能让全文提取耗尽全部预算后仍显示“即将完成”。首版保持连接内串行。

沿用当前未知用量和失败请求暂停复核的默认规则；已完成但用量缺失仍显示未知并保留保守预留。未来如增加启动时的“未知用量按保守预留继续”选项，应作为单独策略与验证事项，不能在本次实现中悄悄改变全局账本语义。

## 8. 成本、风险与收缩方式

### 8.1 成本估算方法

预计请求数 = 第一轮单元数 + 整合节点数 + 各层汇总节点数 + 专题/综合节点数 + 有上限的补查/重试次数。

例如 100 万字符、平均每单元 5,000 字符时，第一轮约 200 次请求；若另有 20 个阶段汇总、6 个专题和 1 个综合节点，基础约 227 次，尚未计入身份整合、额外汇总层、补查、重试和切块重叠。这只是调度规模示例，不是费用或时间承诺。

实际 token 来自模型返回用量；缺失时沿用保守预留，界面区分已知用量与预留。先用有代表性的单元在明确预算内测量，再估算全书与后续汇总余量。费用只有在适用计价信息确认后显示货币估算，不能把 CLI 套餐用量直接写成 API 账单。

### 8.2 风险与处理

| 风险 | 应对与阶段归属 | 不满足时的处理 |
| --- | --- | --- |
| 编码或分章不可靠 | G0030 提供预览、切换编码和按片段退化 | 保留全文，不冒充准确分章 |
| 单元输出截断 | G0031 有界字段与密度检测，G0032 支持版本化拆分 | 保存失败候选，调整单元后按预算继续 |
