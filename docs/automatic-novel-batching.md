# 小说分析自动分批

日期：2026-09-14。

## 行为

在“整本小说分析 → 运行”启用“根据模型上下文自动分批”，先预览批次，再新建或修订分析。目标输入默认 20 万、最多 80 万 token；它是可调的规划目标，实际批次还受输出和模型容量约束。旧运行恢复旧模式，原 TXT 不必重新导入。

已知 DeepSeek 模型按 100 万 token 窗口规划。计数继续采用 UTF-8 字节数加固定余量的保守估算，没有引入不匹配的 tokenizer，也不将估算显示成实测用量。未知模型必须显式填写容量。官方依据：[模型与容量](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[输入与输出总容量限制](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)。

## 实现

- `NovelBatchPlanner` 将连续章节合批，按序列化后的输入、输出预留和窗口剩余量检查每批。模型窗口额外留出 5%（至少 8192 token），规划输出使用上限的 75%；输入和输出预留均是保守规划值。单片段不适合当前容量时先在本地二分，不发送超限父请求。
- 原章节目录和来源快照不改变。运行的 `AnalysisChunk` 可覆盖连续章节，`SectionId` 指向起始章；区间校验逐章保证完整覆盖、无重叠、不跨未选择章节。
- 新提取提示版本 `v6-batch` 按章内片段返回 `Parts`，每片段保留独立六维输出及证据段号。片段编号必须完整且唯一，证据由对应片段契约校验。下游整合仍读取完整事实及来源坐标。
- 已知上下文的请求以模型容量校验，去除与真实窗口不符的固定 25 万字符限制。未知容量请求保留原本地保护。
- 重用既有请求账本、自动二分和节点恢复流程。跨章子批次重算起始章；修订保留成功批次，只重规划待处理区间。
- 运行库升级至 schema 4，升级前使用 SQLite Backup 创建一致性备份，阻止旧程序误执行跨章批次；旧节点的提示、参数和输入指纹继续按原版本读取与恢复。
- 自动模式默认请求超时 15 分钟，可设置 1–15 分钟。累计预算、导入文件容量及其他创作功能不在本次扩容范围。
