# G0003 schema 1 → 2 迁移

作品库 schema 2 的当前 JSON 聚合增加 Revisions 和章节摘要编辑缓冲。物理 project 表仍保存一笔原子聚合，
SQLite user_version 提升为 2，防止旧 G0002 版本在不理解修订账本的情况下覆盖正文并丢失历史。

## 已知版本流程

1. 打开时验证 application_id。版本 2 直接读取；仅支持已知版本 1 的升级，其他版本拒绝。
2. 先验证旧快照；缺少新增字段时使用空修订账本，不把已有编辑稿提升为工作稿或正式稿。
3. 使用 SQLite BackupDatabase 生成同目录 `.before-v2-<唯一标识>.noveldb`，包含已提交的 WAL 内容。
4. 在写事务内再次核对版本为 1，再写入新快照、提升作品写版本并更新 user_version=2。
5. 任一步失败中止打开，保留可用的备份与原事务状态；不盲目覆盖未知新格式。

普通 Save 的 application_id/user_version 校验、旧历史读取、历史前缀保护、预期作品版本比较均在同一写事务内。
其他连接在等待写锁期间改变格式，当前写入也会拒绝，不使用事务外读到的旧格式继续写。

RecoverySnapshot 的新写入格式为 2，防止旧程序忽略修订字段；恢复读取兼容旧格式 1 和新格式 2。
目录库未改变，仍只承担最近项目导航。不存在到未知未来版本的空迁移或自动降级。

迁移和事务使用真实临时 SQLite 文件验证；没有进行发行升级门禁或真实 Host 升级安装。

本文保留 G0003 当时格式。G0004 已升级至 schema 3，当前迁移与恢复约定见 [模板快照契约](../G0004/template-snapshot-contract.md)。
