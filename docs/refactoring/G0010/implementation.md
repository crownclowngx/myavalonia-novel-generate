# G0010 实施方案

日期：2026-09-12。基线 `a14cebd`，承接 G0009 的上下文与 G0008 的统一请求入口。

## 职责与设计思路

`StoryPlanning` 定义可编辑章纲、结构化提案、待采用候选与追加式历史；`PlanningRules` 是无 I/O 的规划验证与采用规则。
`PlanningService` 只构造带来源的提示词、冻结连接、调用请求入口并返回候选，不持有窗口或保存会话。
`MainDocument.Planning` 负责输入、取消、模式和会话更新；存储继续复用现有 SQLite/恢复机制。采用普通记录、组合和明确方法，不增加通用工作流框架。

自动模式收到有效结果即采用；协作模式先保存 Pending，供作者查看后采用。两者共用书籍来源指纹、章纲锁定、卷归属、方法引用和历史不可覆盖检查。
保留作者已有正文、摘要和卷章身份，只补规划；已经接受工作/正式修订的章不能被模型重规划。

## 保存与兼容

作品 schema 升为 7；旧库先用 SQLite 一致性备份，再添加默认 Planning、Chapter.Plan、Volume.Goal。
已有无结构化规划作品保留旧事实策略指纹，不给它们伪造有效章纲。候选、手工草案、方法事件与历史均随作品保存；
另存副本重映射历史的书内身份并清空待采用候选。关闭预检只保存，真正释放才冻结，避免其他工具否决关闭后无法继续编辑。

上下文现在必带全书主线和当前卷目标；变更会让旧预览失效。方法原文在规划任务中完整提供，不能因普通上下文可选预算而被省略。
模型输出必须通过 JSON 对象契约、3–5 章数量、卷序与逐字方法引用检查；失败保留请求记录，不隐式重试。

详细边界见 [规划契约](planning-contract.md)，证据见 [结果](result.md)。
